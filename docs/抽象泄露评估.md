# 云园慧控抽象泄露评估

**作者**：周茂森

**文档定位**：`docs/` 系统设计文档系列第二篇。本文盘点当前代码库中的抽象泄露，逐项评估其危害与处置状态，并给出行动项。全部结论以仓库代码为证据，计数截至 2026-08。

---

## 第一章　概念与评估框架

### 1.1 什么是抽象泄露

**定义**：抽象泄露（Leaky Abstraction）指一层抽象未能完全隐藏其底层复杂性——底层细节在某些场景下「渗」出来，使用者必须理解底层才能正确使用该抽象。该概念因 Joel Spolsky 的《The Law of Leaky Abstractions》（2002）广为人知，其定律为：**所有非平凡的抽象，都有某种程度的泄露。**

由此推出本文的评估立场：泄露不可消灭，工程上有意义的问题是**漏出来之后有没有被接住**。

### 1.2 处置状态分级

本文将每个泄露点归入三档：

| 档位 | 含义 | 典型手段 |
| --- | --- | --- |
| **已接住** | 存在结构性围栏，违反即编译错误或测试失败 | 单一实现、类型约束、完备性测试 |
| **已记录** | 无结构性围栏，但泄露及其对策有明确文档，靠纪律执行 | 模块决策文档、README 规则 |
| **裸露** | 既无围栏也无系统性记录，正确性靠每个开发者每次都记得 | —— |

## 第二章　平台层泄露：SpacetimeDB 渗入领域模型

### 2.1 `FilterableValue` 密封 trait →「无园区」表达为 0 哨兵【已接住】

SpacetimeDB 的抽象承诺是「表就是普通 Rust 结构体」，但索引过滤参数必须实现密封的 `FilterableValue` trait——`Option<u64>` 与 newtype 都不在其中，带此类列的表无法索引查找。底层索引引擎支持的键类型，就此漏进了领域建模：「不属于任何园区」无法用类型表达，只能用哨兵值 `NO_PARK`（0）。

**接住方式**：哨兵语义收拢至单点（`ReadScope::allows_optional_park` 是唯一定义「0 号行谁可见」的位置）；`park_ref.rs` 模块文档完整记录决策成因——「这是被数据库逼出来的选择，不是偏好」。危害被压缩到：新写 View 时须记得选 `allows_optional_park` 而非 `allows_park`，而这一点有权限文档与代码评审对照（docs/权限模型设计.md §4.3）。

### 2.2 Schema 迁移规则 → 表结构由迁移约束塑形【已记录】

「`publish` 一下即完成升级」的抽象在表结构变更处破裂：修改、删除既有列等于清库；追加列必须携带 `#[default(...)]`，且默认值在 const 上下文求值——整数字面量须带类型后缀（`0u64`）、`Option` 须写 turbofish（`None::<String>`）、带析构器的类型（非空 `String`）根本不可用。这些本属存储与序列化层的细节，直接决定了领域模型的形状：`salary_finance` 做成关联表而非工资表上的一列，动因是迁移约束而非领域语义。

**接住方式**：README 第七节的实测行为表 + 发布前自查两问 + CI 清库开关默认关闭。属「已记录」而非「已接住」——没有测试能拦住一次危险的列变更提交，防线是文档与 CI 变量。鉴于此类变更频率低、后果显眼（publish 当场拒绝），维持现状合理。

### 2.3 宏生成项遮蔽 → 73 处 `#[path]` 注册变通【已接住】

`#[spacetimedb::table]` 宏在模块级生成与 accessor 同名的项，文件级 `mod` 声明与之同名即遮蔽。宏的实现机制漏进了每张表的模块组织：全库 73 处 `#[path = "x.rs"] mod x_table;`。**接住方式**：统一约定 + 违反即编译错误（这是少见的「泄露自带围栏」——写错编译不过）。代价是每张新表付一行样板。

### 2.4 `auto_inc` 占位语义 → 151 处 `id: 0`【裸露，低害】

「插入时自增列填 0 占位」是存储层分配策略的直接暴露，全库 151 个插入点各写一次。危害极低（写错任何非 0 值会得到显式主键冲突或意外主键，测试与评审可见），不值得为其建围栏；如实记录为已知噪声。

### 2.5 View 无时间源 → 会话过期语义分裂【已记录】

确定性求值模型不给 View 时钟，导致同一个「会话是否过期」判定在两侧语义不同：Reducer 当场校验 `expires_at`，View 只能依赖 `sweep_expired_sessions` 定期删行。该泄露渗入共享内核签名——`access.rs` 五个函数携带 `now: Option<Timestamp>` 参数，`None` 即表示「调用方为 View，无法获取时间」。**接住方式**：参数语义与补偿机制载于 `access.rs` 与 docs/权限模型设计.md §2.2。残余风险：清扫周期内已过期会话仍可订阅到数据，属已知且有界的窗口。

### 2.6 模块边界错误模型 → `Err(String)`【泄露转为特性】

跨模块边界（WASM → 客户端绑定）不存在类型化错误通道，269 个 Reducer 只能以字符串报错。本项目把这个泄露翻转成了规范：错误文案即用户界面（中文、说明业务原因、指明出路），前端零翻译层直接展示。泄露没有被掩盖，而是被赋予了职责——这是处置泄露的另一种成熟形态。

## 第三章　自建抽象的内部泄露

### 3.1 软删除过滤：与 `ReadScope` 同构的问题，未享受同等待遇【裸露，首要行动项】

23 张表带 `is_deleted` 列；「已删除的行不可见」这一语义没有集中实现，由每个 View 手写 `.filter(|row| !row.is_deleted)`（views 侧 27 处 + `access.rs` 6 处）。本次评估逐域对账：**当前覆盖完整，无漏网**（investment 8 表 8 过滤、rental 7/7、hr/finance/platform 均对齐、maintenance 与 access_control 无软删表）。

问题在于这份完整性没有任何围栏：漏写一处过滤不会有编译错误、不会有测试失败，表现为已删数据在某个列表里复活。这与 `ReadScope` 类型存在的动机完全同构——它的文档写道「手写三层过滤时漏掉任何一层都是一次越权读取，而漏写不会有任何编译错误」——租户、园区、行主三层都进了类型，唯独软删除留在手写层。

**建议围栏**（仿既有先例，成本一天以内）：完备性测试——扫描 `src/tables` 提取带 `is_deleted` 列的表 accessor，对每个 accessor 断言「至少一个 view 源文件中，该表的读取伴随 `is_deleted` 过滤」；与 `所有挂园区的表都已登记`（`deletion.rs`）同一手法。它接不住「某一个 view 忘了」的全部情形，但能接住「新表建了软删列、view 完全没过滤」这类最常见的回归。

### 3.2 财务词汇表字符串跨域【裸露，次要行动项】

财务流水的类别与方向（「工资支出」「账单收入」「支出」「收入」）是 finance 域的词汇表，但以字符串字面量出现在 3 个域 9 处（`hr/employee/salary.rs`、`platform/migration/{billing, sequence}.rs`）。任何一处拼写不一致，或将来调整类别口径，都表现为财务报表静默分类分裂——无编译错误、无测试失败。

**建议围栏**：在 finance 域建常量模块（如 `finance::vocab::{CATEGORY_SALARY, DIRECTION_EXPENSE, ...}`），跨域写入一律引用常量。改动为纯机械替换，9 处调用点半小时内完成；此后新增类别自然汇聚到一处。

### 3.3 双主键体系【已记录，维持现状】

中心账号 `center_user_id` 与租户业务用户 `SystemUser.id` 是两套独立主键，行主判定用错一套即判定失效。该泄露由 `ReadScope.user_id` 的字段文档显式警告（「不能把两套 id 混为一谈」），并在 docs/权限模型设计.md §2.1 成文。类型层面无法区分两个 `u64`（newtype 被 §2.1 的同一平台限制挡住），文档 + 评审是当前上限，维持现状。

### 3.4 MySQL 历史语义残留【大半已接住】

原系统的 `status` 0/1 整数语义（「除 0 外均视为启用」）经 `normalize_status` 单点归一，但 `status == 1` 判定仍以魔数形式散布 20 处；字符串日期残留 2 个字段（`factory.build_date`、`notice.date`——修列等于清库，只能等待自然消亡或数据迁移窗口）。散布的 `status == 1` 属低害（语义稳定、不再增长），不单独立项。

### 3.5 客户档案软匹配【已记录的债务】

租户档案（`TenantProfile`）与合同（`RentalTenant`）之间没有外键，靠「姓名 + 电话」（`party_key`）软匹配关联。「客户档案」这个抽象承诺了稳定身份，实现却是字符串匹配——改名或换号即断链，且该关联参与数据归属判断。这是既有架构评审中已登记的债务（补外键列受 §2.2 迁移规则约束），本文重申其性质：**它是抽象泄露中危害最隐蔽的一类——抽象的承诺与实现的保证不一致**。任何基于档案关联的新功能，设计时必须显式考虑匹配失效场景。

### 3.6 前端订阅生命周期【已接住】

「页面只管渲染数据」的抽象下，SpacetimeDB 的订阅需要显式生命周期管理（进入页面订阅、切换页面退订）。该泄露以显式注册表接住：数据域枚举 `DataScope` 统一登记「路径 ↔ 订阅查询集 ↔ 刷新函数集」，并有对应测试（`每个场景对应的刷新函数集合与预期一致`）拦截登记遗漏。新增页面须三处登记的代价换来了订阅泄漏（该退未退、该订未订）的结构性防护。

## 第四章　结论与行动项

### 4.1 总体评价

本项目对抽象泄露的处置成熟度较高：面对平台层泄露已形成稳定的反应模式——**泄露 → 决策文档（记「为什么」）→ 可行处再加测试围栏（记「不许漏」）**，`NO_PARK`、`ParkChild`、`#[path]` 约定、`DataScope` 注册表均是该模式的产物；`Err(String)` 则示范了第三种形态：无法消除的泄露被翻转为承担明确职责的特性。当前真正的裸露点集中且可收敛。

### 4.2 行动项（按优先级）

| 优先级 | 行动 | 手法 | 预估成本 |
| --- | --- | --- | --- |
| 1 | 软删除完备性测试（§3.1） | 仿 `所有挂园区的表都已登记` 扫描对账 | ≤ 1 天 |
| 2 | 财务词汇表常量化（§3.2） | finance 域常量模块 + 9 处机械替换 | ≤ 半天 |
| 3 | 其余各项维持现状 | 已有围栏或文档；成本收益不成立 | —— |

### 4.3 评审准则

新代码评审时对照三问：

1. 这次改动是否让某个底层细节第一次渗进了上层？若是，先写决策文档再合并；
2. 渗出的细节是否要求「每处使用都记得做某件事」？若是，评估能否用类型或完备性测试接住；
3. 接不住的，是否已在对应模块文档留下警告与对策？
