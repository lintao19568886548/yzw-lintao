# 云园慧控设备管理模块说明

**作者**：周茂森

**文档定位**：`docs/` 系统设计文档系列第十一篇。本篇定义**设备管理**这个分组的边界与内部分类，并记录摄像头、门禁设备台账的实现。第一至三章是分类与边界（不需要技术背景），第四章起是台账设计与实现细节。**除厂商平台适配器与在线告警外（第八章），本篇内容均已实现。**水电表部分见 [智能水电表管理.md](智能水电表管理.md)，不联网设施见 [变压器台账与扫码巡检.md](变压器台账与扫码巡检.md)。

## 第一章　为什么把「数据采集」改成「设备管理」

原来的分组叫「数据采集」，下面只挂了智能抄表一个入口。这个名字有两处不成立：

1. **它描述的是动作，而非对象。**「采集」是设备诸多行为之一，并非分组所容纳的对象。门禁道闸纳入之后，其主要职责为开闭闸门而非采集——该名称即无法涵盖。
2. **它把方向说死了。**采集只有一个方向：设备 → 系统。而门禁、照明、风机这类设备是反方向的：系统 → 设备。一个只描述入站的名字，容纳不了出站的一半。

改成「设备管理」之后，分组名描述的是**对象**（园区里所有联网设备），方向由下一层的分类去区分。

同时「智能抄表」改为「智能水电表管理」：抄表是这一页做的事之一，但它还要做设备绑定、看在线状态；更重要的是，**水电表只是设备的一类**，名字里要有「水电表」，才能和后面的摄像头、门禁并列。

## 第二章　设备的两分法：传感器与执行终端

### 2.1 定义

| | 传感器 | 执行终端 |
| --- | --- | --- |
| 干什么 | 读取物理世界的状态，输出数据 | 接受系统指令，改变物理世界的状态 |
| 数据方向 | 设备 → 系统 | 系统 → 设备 |
| 系统对它的动作 | 读 | 下发 |
| 举例 | 电表、水表、摄像头、温湿度、烟感、液位 | 门禁道闸、电控门锁、人行闸机、照明与风机控制、广播 |

### 2.2 判定标准只有一句话

> **这台设备坏了，是「少了一份数据」，还是「有人被挡在门外」？**

前者是传感器，后者是执行终端。

这句话看起来只是个分类口诀，实际上它**决定了告警等级和处置路径**——这才是做这个分类的目的，否则它只是个标签：

| | 传感器离线 | 执行终端离线 |
| --- | --- | --- |
| 直接后果 | 账单那一行是空的，用量算不出来 | 门开不了或关不上，人和车堵在现场 |
| 可容忍时长 | 按天。月底结账前修好即可 | 按分钟。当场就有人在门口等 |
| 该通知谁 | 财务、物业，进日报 | 值班人员，立即推送 |
| 巡检方式 | 看「回传覆盖」百分比 | 看在线心跳，断开即报 |

**同一套设备台账，两种完全不同的运维节奏。**分类不做在数据里，这两种节奏就只能靠人记住哪台是哪台。

### 2.3 一体机怎么归类

现实里存在既读又控的设备，最典型的就是门禁一体机：刷卡读头是传感器，门锁继电器是执行终端；带对讲和补光的摄像头也沾两头。

**处理办法：一台设备只打一个主分类，按「失效后果更严重的那一面」定。**门禁一体机归**执行终端**——读卡失败只是识别不了，锁不动才是真出事。

不采用「一台设备可以同时属于两类」的能力位方案，原因是分类的用途是决定处置路径，而**一台设备只能有一条处置路径**。允许多标签，告警规则就会遇到「这台设备既该按天也该按分钟」这种没有唯一答案的情况。次要能力写进设备的备注或能力字段供人参考，但不参与分类。

## 第三章　边界：什么进这个分组，什么不进

这一章比分类更重要——分错类只是标签不准，边界画错会导致同一件事在两个模块里各做一遍。

### 3.1 与「门禁管理」的边界

现有「门禁管理」分组下是车辆出入管理、访客管理、访客登记。**这三样都不搬进设备管理**，因为它们记的是业务事实，不是设备。

> **门禁管理回答「何人进入」，设备管理回答「闸门能否正常开闭」。**

设备管理里要新增的是**门禁设备台账**：这个园区装了几台门禁、装在哪个门、什么型号、现在在不在线。它与门禁管理的关系是：一条通行记录来自哪台设备——用设备号关联，两边各管各的。

如果把访客登记搬进设备管理，就会出现「为了查一个访客记录，先要点开设备管理」的荒唐路径；反过来把设备台账塞进门禁管理，则摄像头无处安放——摄像头不产生通行记录。

### 3.2 与「维护管理」的边界

维护管理下已经有变压器、电梯、消防设施，它们显然也是「设备」。为什么不合并？

> **判定标准：这台设备的状态，是它自己报上来的，还是人到现场看来的？**

| | 设备管理 | 维护管理 |
| --- | --- | --- |
| 状态来源 | 设备联网自己上报 | 人到现场巡检，扫码填写 |
| 状态时效 | 实时或按日 | 上次巡检那一刻 |
| 人什么时候去现场 | 坏了才去 | 按周期必须去 |
| 现有成员 | 水电表 | 变压器、电梯、消防设施 |

变压器、电梯、灭火器均**不具备回传链路**，其「正常」状态来自巡检记录，可信度取决于最近一次人工查看的时间。若强行将两类并入同一分组，同一张列表中会并列出现「设备自行上报在线」与「上月经人工确认正常」——两者的可信度相差一个量级，并列呈现将造成误导。

留一个口子：等电梯装了物联网模块、变压器装了在线监测，它们会**同时**出现在两处——设备管理看在线状态和实时告警，维护管理看巡检记录和法定检验周期。这不是重复，是同一台设备的两种状态来源，本来就该分开看。

### 3.3 归类总表

| 设备 | 分类 | 归属分组 | 现状 |
| --- | --- | --- | --- |
| 电表 | 传感器 | 设备管理 | 已上线（`utility_meter`） |
| 水表 | 传感器 | 设备管理 | 已上线（`utility_meter`） |
| 摄像头 `camera` | 传感器 | 设备管理 | 已上线（`device_asset`） |
| 门禁一体机 `access_controller` | 执行终端 | 设备管理 | 已上线（`device_asset`） |
| 车辆道闸 `barrier` | 执行终端 | 设备管理 | 已上线（`device_asset`） |
| 人行闸机 `turnstile` | 执行终端 | 设备管理 | 已上线（`device_asset`） |
| 变压器 | 不联网 | 维护管理 | 已上线，扫码巡检 |
| 电梯 | 不联网 | 维护管理 | 已上线，扫码巡检 |
| 消防设施 | 不联网 | 维护管理 | 已上线，扫码巡检 |
| 车辆 / 访客通行记录 | 业务记录，非设备 | 门禁管理 | 已上线 |

## 第四章　台账怎么放：一个分组，两张表

此处最易出现的错误判断是「既然同属设备，即应建立一张大表将水电表一并纳入」。**不应如此处理。**

`utility_meter` 承载的不只是设备身份，还有**计费口径**：互感器倍率、分时计量标志、挂在哪份合同下按什么单价。这些字段对摄像头毫无意义。更为关键的是，账单明细、合同报价与水电费计算均引用 `meter_id`——迁移表计即等同于变动账目，历史账单将随之受到影响。

正确的做法是**新设备类型走新表，展示层汇总**：

| | 水电表 | 其他设备 |
| --- | --- | --- |
| 表 | `utility_meter`（现有，不动） | `device_asset`（新建） |
| 特有字段 | 倍率、分时标志、账单引用 | 厂商、型号、通道号 |
| 谁引用它 | 账单明细、合同报价 | 门禁通行记录 |

设备管理的总览页把两张表**在读的时候合并**成一份清单，按传感器／执行终端分两栏展示。写入仍然各走各的通道。**一个分组、两张表，而不是一张大表。**

`device_asset` 的字段（`server/spacetimedb/src/tables/device/asset.rs`）：

| 字段 | 说明 |
| --- | --- |
| `asset_id` | 主键，自增 |
| `park_id` | 必填。所有设备都属于某个园区 |
| `factory_id` | `0` 表示园区公共区域（大门、道路、围墙），沿用变压器的 0 哨兵。**门禁与摄像头在这里为 0 是常态**，所以不再往下细分楼层 |
| `device_class` | `sensor` / `actuator`，即传感器／执行终端。**由服务端从 `device_type` 推导，输入结构里没有这个字段**（见下） |
| `device_type` | `camera` / `access_controller` / `barrier` / `turnstile` |
| `device_code` | 设备编号，园区内唯一——现场贴的标签认的就是它 |
| `device_name` / `location` | 名称与位置描述，都必填 |
| `vendor` / `model` | 厂商与型号，报修和换件时要用 |
| `external_device_id` | 厂商平台上的设备号，可空。**全租户唯一**，与水电表同一条理由：同一台设备绑两行台账会让同一份状态被两处各认一次 |
| `commissioned_on` / `remark` / `is_deleted` / `created_at` / `updated_at` | 常规字段 |

现场照片走独立的 `device_asset_image` 关系表，最多 8 张，与维护设备同一口径。

### 4.1 分类不接受客户端传入

`device_class` 存在库里，但**输入结构 `DeviceAssetInput` 里没有这个字段**——服务端一律由 `check_device_type` 从 `device_type` 推导后写入。

这样做同时拿到两件事：

- **客户端不必再抄一份分类表。**前端读 `device_class` 就能分栏，不需要在两处各维护一份「哪种类型算传感器」。
- **「摄像头被标成执行终端」这种自相矛盾的行在结构上写不进去。**若分类由客户端传入，两侧的映射表终将出现漂移，而漂移之后不会有任何环节报错——仅表现为某台设备被归入错误的分栏。

分类的唯一定义因此只有一处：`check_device_type`（`server/spacetimedb/src/reducers/device/asset.rs`）。

### 4.2 改类型要两边的权限

`update_device_asset` 会**同时**要求「原分类那一页」和「新分类那一页」的菜单权限。

若不作此处理，「在摄像头页将一台设备改为道闸」即构成一条绕过门禁设备权限的后门：仅具摄像头权限的账号，可借此创建其本无权登记的道闸。

### 4.3 园区注销时随园区一起注销

`ParkChild::DeviceAsset` 登记为 `Cascade`：设备台账不含巡检历史一类子记录，亦不涉及账目，为删除园区而逐台删除摄像头并无必要。级联仅标记软删除，不改动图片关联——软删除的语义为数据保留、仅从台账中隐藏，若将图片一并解除关联，则不属隐藏而属丢失。

### 4.4 在线状态与视频流都不落库

在线状态实时向厂商平台取，理由与读数不落库一致（[智能水电表管理.md](智能水电表管理.md) §5.2）；视频流更不能进，本系统只记「哪里有几个摄像头、对应平台哪一路」，点击跳厂商平台看画面。

因此 `device_asset` 里**没有任何状态列**——一张始终滞后的状态表，较之不提供状态更易导致误判。

## 第五章　菜单结构

### 5.1 现在

```text
设备管理
  ├ 设备总览          /device/overview   按传感器／执行终端两栏汇总
  ├ 智能水电表管理     /smart-meter/*     传感器
  │    ├ 电表管理
  │    └ 水表管理
  ├ 摄像头管理        /device/camera     传感器
  └ 门禁设备管理      /device/access     执行终端
```

### 5.2 总览显示的是接入率，不是在线率

总览页那一列叫「已接入平台」，数的是**填了平台设备号的设备台数**。

此措辞为有意选择：填写设备号仅表明**具备**获取状态的条件，并不代表当前在线。真实的在线率必须向厂商平台实时查询，而摄像头与门禁的相应链路尚未接入（第八章）。将一个台账口径的数值标注为「在线率」，会使人误认为系统正在监控设备——其后果较不予显示更为不利。

水电表的实时回传情况在智能水电表管理页看「回传覆盖」，总览页给出跳转，不重复计算。

### 5.3 为什么不把「传感器／执行终端」做成菜单层级

看起来很自然的做法是：

```text
设备管理
  ├ 传感器
  │    ├ 智能水电表管理
  │    └ 摄像头管理
  └ 执行终端
       └ 门禁设备管理
```

**不采用。**两个原因：

1. **点到页面要三下。**分类只有两个值，却让每个页面都深一层，日常最常用的水电表页从两级变三级。
2. **分类的价值不在导航，在聚合与筛选。**用户想按分类看的时候，要的是「所有传感器现在有几台离线」这种**跨设备类型的横向视图**——那是总览页里的两栏和筛选器该干的事，菜单树给不了。菜单按设备类型分，总览按设备分类分，各司其职。

## 第六章　权限

沿用现有模式，每个设备页一个菜单权限码：

| 页面 | 权限码 | 状态 |
| --- | --- | --- |
| 电表管理 | `smart-meter:electric` | 已有 |
| 水表管理 | `smart-meter:water` | 已有 |
| 设备总览 | `device:overview` | 新增 |
| 摄像头管理 | `device:camera` | 新增 |
| 门禁设备管理 | `device:access` | 新增 |

**已有的两个权限码不改。**权限码是角色授权表的实际引用键，改名等于把生产环境里已经配好的权限静默作废。菜单显示名可以随便改（连接时按模板键幂等回写），权限码不行。

同理，`/smart-meter/meter` 与 `/smart-meter/water` 两个路由路径也保持不变——路径不出现在界面上，改它没有任何用户可见收益，却要动路由、权限匹配、侧边栏高亮和测试。

分组自身的模板键与路径也保持旧值 `data-collection` / `/data-collection`，只改了显示名。菜单同步按「模板键或路径」匹配已有记录，若两者同时修改将无法匹配原有记录，进而在生产库中插入一条重复菜单。此两项取值均不在界面上呈现。

### 6.1 设备总览对能看见分组内任意一页的账号开放

`/device/overview` 自己有一条菜单，管理员可以单独授予；同时它在路由守卫里被登记为「能看见设备管理分组下任意一页就能看」——与运营总览、财务总览、数据地图同一处理。

否则将出现如下情形：分组更名完成、页面亦已上线，但在新菜单完成授权之前，全部非 Super 账号所见的设备管理与此前完全一致。

它只显示台数，行级数据范围仍由服务端 `my_device_assets` 按园区约束。

**摄像头页与门禁设备页不互相放行。**这是两个不同的权限面，服务端 Reducer 也是按这两条路径分别校验的（§4.2）。

### 7.1 更名（不改任何行为、路径与权限码）

| 位置 | 原 | 现 |
| --- | --- | --- |
| 侧边栏分组 | 数据采集 | 设备管理 |
| 侧边栏分组图标 | 水表表盘 `meter` | 芯片 `device` |
| 侧边栏子项 / 页面标题 | 智能抄表 | 智能水电表管理 |

| 页内切换按钮 | 电表抄表 / 水表抄表 | 电表 / 水表 |
| 账单页按钮 | 从智能抄表带入读数 | 从智能水电表带入读数 |
| 园区档案页字段 | 智能抄表设备 | 智能水电表设备 |

**「抄表」作为行业术语予以保留**：抄表日、本月抄表数、手工抄录等表述不予改动——它们指称行业内的具体动作，而非本模块的名称。若将动作名称一并更改，只会造成既有使用者理解困难。

### 7.2 设备台账

| 层 | 文件 | 内容 |

| 表 | `server/spacetimedb/src/tables/device/` | `device_asset`、`device_asset_image` |

| 事务 | `server/spacetimedb/src/reducers/device/asset.rs` | 增改注销三个 Reducer、类型与分类校验、两处唯一性校验 |

| 页面 | `src/pages/device/` | 总览、摄像头管理、门禁设备管理 |

## 第八章　未实施

两项卡在外部条件上，不是没做：

1. **摄像头与门禁的接入通道。**方案已定：**不走厂商云平台，改为在园区现场部署自研边缘计算设备，由边缘设备主动连我们的服务器**——园区网络在 NAT 后面，反方向根本走不通；而且边缘设备有心跳，在线状态是它的副产品。视频流不出园区，AI 识别在边缘设备上完成，只回传结构化事件，与「服务器不承担 AI 计算」那条约束一致。完整设计见 [边缘计算设备与摄像头接入.md](边缘计算设备与摄像头接入.md)，同样尚未实施。落地后总览页的「接入率」即可换成真正的在线率。
2. **在线告警的分级下发。**第二章 §2.2 那张表描述的两种节奏（传感器按天、执行终端按分钟）需要通知通道支撑，当前系统没有实时推送能力。这一项还依赖第 1 项——没有在线状态就没有告警源。

此外，设备台账目前**不做扫码巡检**。摄像头和门禁的状态应当由平台上报，不该靠人到现场扫码确认；真要靠人看的设备，它属于维护管理（§3.2）。等平台接口接上之前，这两页是纯台账。
