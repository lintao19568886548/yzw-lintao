# 云园慧控权限模型设计

**作者**：周茂森

**文档定位**：本文是 `docs/` 系统设计文档系列的第一篇，专题讲解本系统如何在 SpacetimeDB 上实现精细的权限划分。阅读前建议先读 [server/ARCHITECTURE.md](../server/ARCHITECTURE.md) 第一章（SpacetimeDB 平台概念）——本文假设读者已理解 Table / Reducer / View / Identity 四个基本概念（下文以 §A1.x 指代该文档章节）。

**本文的事实基准**：全部结论出自仓库当前代码，核心文件为 `server/spacetimedb/src/access.rs`（权限内核，含 12 个以中文命名的判定规则测试）、`server/spacetimedb/src/reducers/shared/access.rs`（Reducer 侧门卫）、`server/spacetimedb/src/views/platform/permissions.rs`（权限查询 View）。

## 第一章　权限问题的定义与总体思路

### 1.1 业务图景：谁在用这个系统

在讲任何机制之前，先交代系统为谁而建——权限模型的每一条规则都对应下面这个现实结构：

本系统是给**园区老板**（园区运营方）使用的管理软件。老板名下有多个园区；每个园区设一名**园区经理**，管理该园区内各厂房的人、事、物，维持厂房的正常运行，为租客提供便利。维护园区各项设施（变压器、电梯、消防设备等）的正常运行是园区方的职责——系统的维护域（消防记录、变压器、电梯、维修工单）因此存在。

**租客**——承租厂房的客户——是园区服务的对象，**不登录本系统**：它们在系统中以业务数据出现（租赁合同、客户档案、账单），而不是账号。反过来说，系统中的每一个账号都必定属于运营方的一名工作人员——老板、园区经理、财务、人事、维修人员等；人事域的员工、考勤、请假记录，管理的正是这批持有账号的人自己。

现实角色与权限机制的对应关系，就是全文要展开的内容：

| 现实角色 | 权限机制上的落点 | 详见 |
| --- | --- | --- |
| 园区老板 | `Super` 角色：全部园区、全部菜单、全部职能 | §3.6 |
| 园区经理 | 普通角色 + 园区授权（`RolePark` / `UserPark`）收窄到所辖园区 | §3.3、§4.3 |
| 财务、人事等职能岗位 | 菜单授权划定页面，权限码与职能（Duty）划定操作与数据 | §3.5、§4.4 |
| 租客 | 不是账号，是数据行——不参与权限判定 | — |

**术语约定**：使用本系统的一家园区运营公司，本文称**运营方**——即多租户架构意义上的「租户」，对应数据模型中的 `customer_id`（见第二章）。本系统源自 SaaS 产品，同一套部署可服务多家运营方，隔离机制由此而来。「租户」与「租客」（承租厂房的客户）字面过近、极易混读，因此正文一律写「运营方」，「租户」只出现在本条说明与代码注释的引文里。（代码里两种含义并存：`user_tenant_mapping` 的 tenant 指运营方，`RentalTenant` 的 tenant 指租客——历史命名如此，文档以中文术语为准。）

### 1.2 权限要回答的五个问题

本系统的权限体系不是单一的「是否管理员」判断，而是对以下五个独立问题分别给出答案：

| # | 问题 | 承载机制 | 详见 |
| --- | --- | --- | --- |
| 1 | 当前账号属于哪家运营方 | 身份链条与 `customer_id` | 第二章 |
| 2 | 当前账号拥有哪些角色 | `UserRole` → `Role` | 第三章 |
| 3 | 能进入哪些页面 | `RoleMenu` → `Menu`（动态菜单） | 第六章 |
| 4 | 能执行哪些操作 | 权限码（`RoleCode` / `UserCode`）与 Reducer 门卫 | 第五章 |
| 5 | 能看到哪些数据行 | `ReadScope`：运营方 × 园区 × 行主 × 职能 | 第四章 |

角色名称本身不回答其中任何一个问题（`Super` 是唯一例外，见 §3.6）。业务代码一律检查关系表、权限码与数据范围，不检查角色叫什么名字。

### 1.3 平台结构为什么使精细权限成为可能

传统技术栈实现行级权限有两条路：应用服务器中间件（每个接口手写过滤，容易漏）或数据库行级安全策略（如 PostgreSQL RLS，用受限的 SQL 表达式描述）。SpacetimeDB 提供了第三条路，也是本系统的地基：

- **127 张表全部私有**——客户端在物理上不存在任何未经过滤的读取途径；
- **117 个 View 全部按调用者身份实时计算**——行级安全写成普通 Rust 函数，以 `ctx.sender()` 为隐式参数逐行判定，表达力不受 SQL 策略语言限制；
- **269 个 Reducer 是唯一写入口**——每个写入在事务内先鉴权后执行。

换言之：读取面**不存在**「忘记设权限」的可能——没有无过滤的读取面存在；写入面的鉴权则由门卫函数与类型系统约束（第五章）。

### 1.4 单一事实来源

权限判定只有一份实现：`src/access.rs`。Reducer 与 View 的上下文类型不同，但 `DbContext::db_read_only()` 对两者返回同一个 `LocalReadOnly`，因此身份解析与授权判定不需要写两遍。该文件的模块文档记载了这样设计的直接原因：

> 判定逻辑不需要写两遍——写两遍就会像历史实现那样悄悄长出行为差异（View 侧曾经漏掉禁用用户和菜单租户归属校验）。

这是一次真实事故的记录：读写两侧各自实现权限判定时，View 侧遗漏了「用户被禁用」的检查——被禁用的账号仍能订阅到数据。收拢为单一实现后，这类分歧在结构上不再可能。

## 第二章　身份链条：从连接到业务用户

### 2.1 两套主键：中心账号与运营方业务用户

系统存在两套相互独立的用户主键，由映射表关联：

| 概念 | 主键 | 说明 |
| --- | --- | --- |
| 中心账号 | `center_user_id`（`CenterUser.id`） | 登录主体：一部手机号一个账号，跨运营方唯一 |
| 运营方业务用户 | `SystemUser.id` | 某家运营方内部的业务身份：角色、园区授权、行主标记都挂在它上面 |
| 映射 | `user_tenant_mapping` | （中心账号，运营方）→ 业务用户；一个中心账号可属于多家运营方 |

`ReadScope` 的字段文档对此有明确警告：两套 id **不能混用**——`center/*` 域的数据以 center 侧 id 标记行主，业务域的数据以 `SystemUser.id` 标记行主，用错一套即判定失效。

### 2.2 身份解析的完整链条

每次 View 或 Reducer 调用，身份都从连接现场重新解析（不缓存、不信任客户端传参）：

```text
① Identity（连接令牌，ctx.sender() 获取）
② user_session.identity().find(sender)          —— 登录会话
     Reducer：携带 ctx.timestamp，过期会话被当场拒绝
     View：拿不到时间源，依赖 sweep_expired_sessions 定期删除过期行
     ↳ 找不到会话时回退 user_identity（管理员显式绑定的常驻设备身份，
       供打卡机等无人值守设备使用，不依赖登录会话）
③ center_user.customer_type                     —— 当前运营方（customer_id）
④ user_tenant_mapping                           —— 映射到运营方业务用户 id
⑤ system_user，校验 customer_id 匹配 且 status == 1（未禁用）
```

五步中任何一步失败，整个解析返回 `None`：View 返回空集，Reducer 返回中文错误（「当前身份未绑定用户」「用户已被禁用」）。

### 2.3 Principal：构造成功即证明

解析结果封装为 `Principal`：

```rust
/// 已解析的调用者：启用状态的业务用户，以及它的全部启用角色。
///
/// 能构造出 `Principal` 就意味着「身份已绑定、会话有效、用户未被禁用、
/// 用户属于当前租户」都已成立，后续判定只需要在此基础上加条件。
pub struct Principal {
    pub user: SystemUser,
    pub roles: Vec<Role>,
}
```

这是贯穿整个权限体系的设计手法——**把「已校验」编码为类型**：拿到一个 `Principal` 值本身就是四项不变式成立的证明，下游代码无须重复检查，也无法拿到未经校验的值。同一手法在写入侧再次出现（`AdminContext`，§5.2）。

`roles` 装载时已过滤 `status == 1`（停用的角色即时失效）并去重。

### 2.4 运营方隔离是第一层

原系统以「一家运营方一个 MySQL 库」实现隔离；当前系统将全部运营方放入同一个 SpacetimeDB Module，因此 `Role`、`Menu`、`SystemUser` 及所有业务表都携带 `customer_id` 列。由此产生一条铁律：**一切判定的第一层都是运营方**——View 的第一个过滤条件是 `customer_id`，Reducer 的关联主键校验必须确认目标记录属于调用者当前运营方（§5.5），任何跨运营方的主键引用都是缺陷。

## 第三章　授权数据模型（RBAC）

### 3.1 关系全景

系统采用数据库驱动的 RBAC（Role-Based Access Control，基于角色的访问控制），角色不是代码里的固定枚举，而是管理员在界面上自行创建的数据：

```text
中心账号（CenterUser）
   │
   └── user_tenant_mapping ──→ 运营方业务用户（SystemUser）
                                   │
                                   ├── UserRole ──→ Role ──┬── RoleMenu ──→ Menu   （页面）
                                   │                       ├── RoleCode ──→ Code   （操作）
                                   │                       └── RolePark ──→ Park   （数据范围）
                                   │
                                   ├── UserCode ──→ 直接授予的权限码（不经角色）
                                   └── UserPark ──→ 直接授予的园区范围（不经角色）
```

表定义位置：`tables/hr/role.rs`、`tables/hr/relations/{user_role, role_menu, role_park, user_park}.rs`、`tables/platform/menu.rs`、`tables/platform/permissions/{code, role_code, user_code}.rs`。

### 3.2 并集语义

一个用户可持多个角色，最终权限取**并集**；角色继承的权限码与直接授予的权限码同样合并（`access.rs::held_codes`）：

```rust
fn held_codes(db: &LocalReadOnly, principal: &Principal) -> BTreeSet<String> {
    let mut codes = BTreeSet::new();
    for role in &principal.roles {
        for link in db.role_code().role_code_by_role().filter(role.role_id) {
            if let Some(code) = db.code().code_id().find(link.code_id)
                && code.template_deleted_at.is_none()
            {
                codes.insert(code.code);
            }
        }
    }
    for direct in db.user_code().user_code_by_user().filter(principal.user.id) {
        codes.insert(direct.code);
    }
    codes
}
```

前端的 `my_codes` View 以 `source = "role" / "user"` 区分权限码来源，供权限管理界面展示；服务端判定不区分来源，持有即有效。

### 3.3 园区授权的优先级规则

园区范围有一条与并集不同的特殊规则（`access.rs::visible_parks`，与原系统行为一致）：**用户直接授权优先**——`UserPark` 非空时以它为准，完全没有直接授权时才回退到各角色 `RolePark` 的并集。管理员可以据此为个别用户临时收窄或扩大园区范围，而不必改动角色。

### 3.4 角色范围与层级

- `Role.scope` 区分两类角色：`"system"`（运营方业务角色：财务、人事、园区运营等）与 `"organization"`（组织空间内部角色，须携带 `organization_id`，不能跨组织复用）；
- `Role.parent_id` 构成角色树，子角色的菜单授权不得超过父角色——它是授权上限，不只是界面展示层级。

### 3.5 权限的三种粒度

| 粒度 | 机制 | 典型例子 |
| --- | --- | --- |
| 页面级 | `RoleMenu`：能否进入某个路径 | 能否打开「财务管理」页 |
| 操作级 | 权限码：能否执行某类动作 | `hr:manage`（人事全员数据） |
| 数据级 | 园区范围 + 行主 + 职能 | 同一张财务页内，1 号园区的经理只看到 1 号园区的流水 |

页面可见**不代表**拥有页面内全部操作；能执行操作**不代表**能看到全部数据。三种粒度独立授予、独立校验。

### 3.6 `Super` 特例：唯一的角色名判定

系统管理员是全系统唯一以角色名判定的身份，且判定条件是显式三元组（`Principal::is_admin`）：

```text
role.name == "Super"  且  role.scope == "system"  且  role.status == 1
```

`Super` 拥有全部菜单（不依赖 `RoleMenu`）、全部园区（不依赖 `RolePark` / `UserPark`）、全部职能。除此之外，**任何业务判定都不得依赖角色名**——「财务」「人事部」这类名称只是管理员起的标签，改名不应改变任何人的可见范围（该原则的完整论证见 §4.4）。

## 第四章　读取权限：ReadScope

### 4.1 定义与动机

**定义**：`ReadScope` 是一次读取授权判定所需全部上下文的类型化表达——**运营方 × 园区 × 行主**三层过滤，外加可以放宽后两层的职能标志。每个 View 在入口处解析一次，随后逐行判定全部走它的方法。

类型存在的动机写在它的文档里：

> View 只解析一次 `ReadScope`，随后逐行判定都走它的方法，不再手写过滤条件——手写三层过滤时漏掉任何一层都是一次越权读取，而漏写不会有任何编译错误。

即：把「容易漏写的过滤条件」变成「有名字、可测试、只实现一次的方法」。

### 4.2 构造过程

```rust
pub fn read_scope(db, sender, now) -> Option<ReadScope> {
    let principal = principal(db, sender, now)?;          // 第二章的身份链条
    let unrestricted = principal.is_admin();              // Super 判定，仅此一处
    let park_ids = visible_parks(db, &principal) ...;     // §3.3 的优先级规则
    let codes = held_codes(db, &principal);               // §3.2 的并集
    Some(ReadScope { customer_id, user_id, park_ids, unrestricted, roles, codes })
}
```

一个实现细节：管理员的 `park_ids` 在构造时**同样展开**为本运营方全部园区，而不是留空后到处特判——「按园区索引逐个取行」的 View 对两类账号可以走同一条代码路径。

### 4.3 判定方法语义表

| 方法 | 语义 | 典型使用场景 |
| --- | --- | --- |
| `is_unrestricted()` | 是否不受园区限制（即 Super） | 无园区维度、只分「管理员看全部 / 其他人看自己」的数据 |
| `allows_park(park_id)` | 园区在数据范围内 | 财务流水、合同、账单等挂园区的行 |
| `allows_optional_park(park_id)` | 同上，但 `NO_PARK`（0，未归属园区）的行**仅对不受限账号可见** | 工资支出等公司层面、不挂园区的流水 |
| `parks()` | 迭代数据范围内的园区 id | 按园区索引逐个取行的 View |
| `owns(owner)` / `owns_id(owner)` | 行主是否为调用者本人 | 报销、请假、考勤等个人数据 |
| `has_code(code)` | 是否持有权限码 | 操作级判定 |
| `has_duty(duty)` | 是否具备职能（Super 恒真） | 见 §4.4 |
| `owns_or_has_duty(owner, park_id, duty)` | 本人的行始终可见；具备职能时还能看到**数据范围内**其他人的行 | 工资、报销列表 |

`allows_optional_park` 的规则值得单独强调：园区外键统一以 `u64` + 哨兵 `NO_PARK`（0）表达（原因见 ARCHITECTURE.md §2.9），挂在 `NO_PARK` 下的行属于「公司层面」数据，受园区限制的账号一律不可见——哨兵值的语义只在这一个方法里定义，全部 View 经由它判断。

### 4.4 职能（Duty）：显式授予，不靠名字

**定义**：职能是「可以越过园区或行主限制、多看到一部分数据」的能力。当前有两项：

| 职能 | 授予载体 | 语义 |
| --- | --- | --- |
| `ReimbursementAudit`（审批报销） | `Role.reimbursement_auth` 数值字段 | 可见本人以外、数据范围内的报销申请。以数值而非布尔承载，因为它同时是审批额度 |
| `HrManage`（人事全员数据） | 权限码 `hr:manage` | 可见本人以外的员工、考勤、请假记录 |

职能的设计原则写在 `Duty` 的类型文档里，是整个权限体系最重要的一条纪律：

> 职能必须由**显式授予**决定——权限码关联或角色表上的显式字段——绝不能靠角色名字符串判断。靠名字判断意味着在权限管理页给角色改个名，就会静默改变一批人的可见范围，既不报错也无痕迹。

### 4.5 View 中的使用形态

挂园区的数据（`views/finance/record.rs`）：

```rust
#[spacetimedb::view(accessor = my_finances, public)]
pub fn my_finances(ctx: &ViewContext) -> Vec<Finance> {
    let Some(scope) = current_read_scope(ctx) else { return vec![] };
    let mut finances = ctx.db.finance()
        .finance_by_customer().filter(scope.customer_id.as_str())   // 第一层：运营方
        .filter(|f| !f.is_deleted && scope.allows_park(f.park_id))  // 第二层：园区
        .collect::<Vec<_>>();
    finances.sort_by_key(|f| f.finance_id);
    finances
}
```

个人数据 + 职能放宽（报销、工资类 View 的判定形态）：

```rust
.filter(|row| scope.owns_or_has_duty(row.user_id, row.park_id, Duty::ReimbursementAudit))
```

### 4.6 判定规则即测试

`access.rs` 底部的 12 个中文命名测试构成读取权限的规格说明书，直接罗列即可读懂规则边界：

- `园区范围外的记录不可读`
- `系统管理员不受园区限制`
- `未归属园区的记录对受限账号不可读`
- `本人记录始终可读且不依赖园区`（行主判定优先于园区判定）
- `职能只放宽数据范围内的他人记录`（有职能也看不到园区范围外的数据）
- `人事职能由权限码授予而非角色名`（角色叫「人事部」不产生任何权限）
- `系统管理员具备全部职能`

修改判定规则时，先改测试再改实现；新增职能时，必须为「靠名字不生效、靠授予才生效」补测试。

## 第五章　写入权限：Reducer 门卫

读取隔离靠 `ReadScope`，写入授权靠 `reducers/shared/access.rs` 中的门卫函数族。所有门卫失败时返回面向用户的中文错误（ARCHITECTURE.md §3.2 的文案规范）。

### 5.1 AdminContext：把「已校验」编码为类型

多数管理操作要求系统管理员身份。早期写法是每个 Reducer 第一行手写 `require_admin(ctx)?;`——它的问题被 `AdminContext` 的类型文档记录下来：

> 全仓库有 150 多处 reducer 在函数体第一行手写 `require_admin(ctx)?;`，校验通过后立刻把返回的 `u64` 丢掉——校验这件事本身从未被编码进类型，完全靠「没忘记在第一行调用它」这条人工纪律撑着。这个类型把校验结果变成一个值：拿到 `AdminContext` 本身就是证明，构造入口只有 `AdminContext::require` 一个，不能绕过校验直接造一个出来。

```rust
#[spacetimedb::reducer]
pub fn create_salary(ctx: &ReducerContext, input: SalaryInput) -> Result<(), String> {
    AdminContext::require(ctx)?;    // 唯一构造入口；失败 → 「需要系统管理员权限」
    ...
}
```

这与 `Principal`（§2.3）、`validated_*` 智能构造器（ARCHITECTURE.md §3.1）是同一设计手法的三次应用：**合法性由类型的构造入口保证，而非由调用纪律保证**。

### 5.2 页面权限型门卫：写权限与菜单授权联动

一部分写操作的授权依据是「调用者能否进入对应管理页面」，与动态菜单共用同一份授权数据：

| 门卫 | 要求的菜单路径 | 保护的操作 |
| --- | --- | --- |
| `require_permission_manager` | `/system/role` | 角色、菜单、权限码管理 |
| `require_rental_manager` | `/system/park` 或 `/rental/manage` | 园区、厂房、合同管理 |
| `require_menu_path(ctx, path)` | 任意指定路径 | 通用形式 |

Super 默认通过全部页面判定（`can_access_path` 中 `is_admin()` 短路）。这样设计的效果是：管理员在权限管理页把某角色的「租赁管理」菜单收回，该角色的成员**同时**失去页面入口与对应的写入能力——授权只维护一份。

页面权限型之外还有一类**权限码型门卫**：设施巡检的 `require_inspector` 要求登录账号持有权限码 `maintenance:inspect`（`Super` 恒可），再叠加园区数据范围校验。它不挂菜单——巡检员不需要看到后台维护页，扫设备上的二维码即可填报；变压器、电梯、消防设施共用这一个权限码，一码通检。完整设计见 [变压器台账与扫码巡检.md](变压器台账与扫码巡检.md) §3.4（第五、六篇沿用）。

### 5.3 数据范围型门卫

`require_park_access(ctx, park_id)`：写入挂园区的数据前，校验目标园区在调用者数据范围内（复用 §3.3 的 `visible_parks`）。变体 `require_park_access_unless_archived` 处理已归档园区的特殊场景。

### 5.4 父记录校验族：存在性与运营方归属一次完成

约 20 个 `require_*` 函数（`require_park`、`require_salary`、`require_finance`、`require_rental_tenant`……）承担同一职责：按主键查找目标记录，**同时校验其 `customer_id` 与调用者当前运营方一致**，任一不满足即返回「XX 不存在」。这是 §2.4 运营方铁律在写入侧的落点——跨运营方的主键引用在门卫处被统一拦截，且对外不区分「不存在」与「不属于当前运营方」（不泄露其他运营方的存在性）。

### 5.5 写入侧小结

一个业务 Reducer 的标准鉴权序列（对照 ARCHITECTURE.md §2.2 的外壳结构）：

```text
① 身份门卫：AdminContext::require / require_menu_path / 本人判定
② 数据范围门卫：require_park_access（涉及园区时）
③ 父记录门卫：require_*（涉及关联主键时，含运营方归属校验）
④ 业务校验：validated_* 纯函数
⑤ 事务写入
```

## 第六章　前端侧：菜单、路由与权限的呈现

### 6.1 权限查询 View

前端经以下 View 订阅权限数据（`views/platform/permissions.rs`）：

| View | 内容 | 用途 |
| --- | --- | --- |
| `my_roles` | 调用者的启用角色 | 界面展示 |
| `my_menus` | 经 `RoleMenu` 计算的可见菜单 | 侧边栏与路由守卫 |
| `my_codes` | 持有的权限码（标注 `source`） | 按钮级显隐 |
| `manageable_roles / _menus / _parks / _role_menus / _role_parks` | 管理员可操作的授权数据 | 权限管理页 |

菜单进入侧边栏须同时满足五个条件：`Menu.status == 1`、`template_deleted_at` 为空、`template_internal_only == false`、调用者经角色获得有效 `RoleMenu`、菜单路径与 Dioxus `Route` 一致。

### 6.2 前端权限是用户体验，不是安全边界

必须明确：前端依据 `my_menus` / `my_codes` 隐藏入口与按钮，仅为避免用户看到点击后必然失败的功能项。**真正的边界全部在服务端**——View 的 `ReadScope` 决定订阅得到什么，Reducer 的门卫决定调用能否成功。攻击者绕过前端直接调用 Reducer 或订阅 View，得到的结果与在界面上操作完全一致。因此前端权限缺陷是体验问题，服务端权限缺陷才是安全事故，两者的修复优先级不同。

### 6.3 新增页面的授权检查清单

新增或迁移一个后台页面时，依次完成：

1. 在 Dioxus `Route` 中声明真实路径；
2. 在 `Menu` 表中创建相同路径的菜单；
3. 明确哪些角色获得 `RoleMenu`——**不得默认授权所有角色**；
4. 为页面内新增、修改、删除、审核等操作定义权限码；
5. Reducer 中落实第五章的鉴权序列；
6. View 中落实第四章的三层过滤；
7. 分别以普通角色与 `Super` 验证菜单可见性与数据范围；
8. 面向匿名访客的公开页面确认不订阅任何后台敏感 View。

## 第七章　设计准则汇总

全文的规则收拢为七条，供评审时对照：

1. **单一事实来源**：权限判定只在 `src/access.rs` 实现一次，View 与 Reducer 共用（§1.4）；
2. **运营方是第一层**：一切读取先过 `customer_id`，一切主键引用先校验运营方归属（§2.4、§5.4）；
3. **构造即证明**：`Principal`、`AdminContext` 的合法性由唯一构造入口保证，不靠调用纪律（§2.3、§5.1）；
4. **显式授予，不靠名字**：除 `Super` 三元组外，任何判定不得依赖角色名（§3.6、§4.4）；
5. **并集与优先级**：多角色权限取并集；园区授权用户直授优先于角色回退（§3.2、§3.3）；
6. **三层过滤类型化**：View 不手写过滤条件，逐行判定走 `ReadScope` 方法（§4.1）；
7. **规则即测试**：判定规则以中文命名测试固化，改规则先改测试（§4.6）。
