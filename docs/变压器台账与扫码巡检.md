# 云园慧控变压器台账与扫码巡检设计方案

**作者**：周茂森

**文档定位**：`docs/` 系统设计文档系列第四篇。本篇最初是设计方案，经逐条确认后已于 2026-08-04 **实施完毕**（代码全部落地，随下一次正常部署上线）——现在同时是该功能的实现记录。第一章的「现状」描述的是改造前的旧模型，保留作为决策背景。

---

## 第一章　现状与问题

### 1.1 现状

当前变压器功能（维护管理 → 变压器管理）只有一张 `transformer` 表（`server/spacetimedb/src/tables/maintenance/transformer.rs`），一行同时承载两类信息：

- **设备信息**：`transformer_name`（可空）、`specifications`、`park_id`、`factory_id`；
- **巡检信息**：`status`、`checker`（自由文本）、`check_time`、图片（`transformer_image` 关联表）。

页面上的「新增记录」就是插入一行——设备名称与规格每次重新键入。

### 1.2 问题

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 设备与巡检记录合并于一行，变压器不具备独立的台账身份 | 同一设备的历史巡检只能依据名称文本推断归属，而该名称尚可为空 |
| 2 | 没有位置信息 | 一个园区可能有几台变压器，分不清哪台在哪（现有 `address` 字段是历史遗留的联系地址，不是设备位置） |
| 3 | 检查人是自由文本 | 谁都能替谁填，无法追责——与「维护信息必须由持有账号和巡检权限的人填写」的要求相悖 |
| 4 | 巡检必须登录后台网页 | 现场设备旁不方便操作，巡检记录容易断档 |
| 5 | 设备属性寄居在别的对象上 | 老系统把变压器容量（表单显示 `11.00 KW`）记在**厂房**表单里，设备自己反而没有容量字段 |

正确的业务模型是：**先有变压器（资产），后有巡检（事件）**——变压器长期存在于园区的某个位置，定期维护产生一条条巡检记录。

生产数据现状（2026-08-04 实查）：`transformer`、`firefighting`、`elevator` 三表行数均为 **0**——尚无存量数据，**不需要数据迁移**，新模型可以直接取代旧表。

## 第二章　目标数据模型：资产与巡检分离

### 2.1 两个概念

- **资产**：设备本体，长期存在，有名字、位置、规格；增删改是低频管理操作。
- **巡检记录**：一次维护事件，附着于某台资产；只增不改，随时间累积成该设备的履历。

### 2.2 变压器资产表 `transformer_asset`（新表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `asset_id` | `u64` PK auto_inc | 台账主键，二维码即由它生成 |
| `customer_id` | `String` | 运营方隔离，第一层 |
| `park_id` | `u64` | **必填非 0**——变压器必须属于某个园区 |
| `factory_id` | `u64` | `0` = 园区公共区域（配电房、室外），沿用既有哨兵约定 |
| `transformer_name` | `String` | **必填**——台账里的设备必须叫得出名字（如「1 号变压器」） |
| `location` | `String` | **必填**——位置描述（如「3 号厂房西侧配电房」），解决「哪台在哪」 |
| `specifications` | `String` | 规格型号（如 `SCB13-1250kVA`） |
| `capacity_centi_kw` | `u64` | 容量，单位**千瓦（kW）**，×100 整数存储（沿用 `centi_*` 定点数约定），展示如 `11.00 kW` |
| `commissioned_on` | `Option<String>` | 投运日期 `YYYY-MM-DD`，可选 |
| `remark` | `Option<String>` | 备注 |
| `is_deleted` / `created_at` / `updated_at` | — | 软删除与时间戳，全库统一口径 |

索引：`by_customer`、`by_park`、`by_factory`。

**资产图片**：新关联表 `transformer_asset_image`（沿用 `park_image` / `transformer_image` 的既有三段式模式），存设备铭牌、安装环境照片。

### 2.3 巡检记录表 `transformer_inspection`（新表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `inspection_id` | `u64` PK auto_inc | |
| `customer_id` | `String` | |
| `asset_id` | `u64` | **必填外键** → 资产；巡检必须落在具体设备上 |
| `status` | `String` | 运行状态（正常 / 异常） |
| `abnormal_note` | `Option<String>` | 异常描述——状态为异常时**必填**（校验纯函数保证） |
| `inspector_user_id` | `u64` | **由登录会话自动记录**（`SystemUser.id`），不再手填文本 |
| `inspector_name` | `String` | 巡检人姓名，写入时从账号快照——历史记录应当冻结当时的名字，维护域订阅里也没有用户表可供前端反查 |
| `check_time` | `Timestamp` | 默认取提交时刻（`ctx.timestamp`），允许显式传入以补录 |
| `remark` | `Option<String>` | 随行人员等补充说明 |
| `created_at` | `Timestamp` | |

索引：`by_customer`、`by_asset`、`by_check_time`。

**巡检图片**：新关联表 `transformer_inspection_image`，存现场照片。

**巡检记录只增不删**：不提供修改与删除入口——服务端不为它实现更新或删除 Reducer；填错了补一条更正记录。`inspector_user_id` 取自 `Principal`（权限模型设计.md §2.3）——提交人身份由登录会话决定，不可代填、不可伪造；配合 §3.4 的权限码要求，共同落实「**持有账号和巡检权限的人才能填写维护信息**」。

### 2.4 旧表处置

SpacetimeDB 2.6.1 不允许对已有表增删列（ARCHITECTURE.md §2.6.1 实测规则），因此不能在 `transformer` 上加 `asset_id`——必须新表。生产旧表为空，无迁移步骤。核实 §2.6.1 后确认**删除已发布的表同样被官方列为禁止**，因此旧 `transformer` 与 `transformer_image` 两张表保留为空壳（表定义带弃置说明，不再有任何 Reducer 或 View 读写它们），旧的三个 Reducer 与两个 View 已移除。

## 第三章　巡检二维码与扫码流程

### 3.1 原则：二维码是入口，不是授权

码的内容是一个普通 URL：

```text
https://yz.furong.org/maintenance/inspect/transformer/{asset_id}
```

**不含任何密钥或令牌**。贴在设备上的码随时可能被拍照外传，因此拿到码绝不等于有权写入——真正的边界是登录身份与服务端门卫（呼应 权限模型设计.md §6.2「前端权限是用户体验，不是安全边界」）。码只解决一件事：让巡检员免于在手机上找页面、选设备。

### 3.2 生成与张贴

- 前端用仓库**既有依赖** `qrcode`（`Cargo.toml` 已声明，带 `svg` 特性）本地生成 SVG，不依赖外部服务；
- 资产详情提供「巡检码」弹窗：二维码 + 设备名 + 位置，弹窗内「打印」按钮直接出标签——打印时页面临时进入打印模式，只输出标签区域（黑字白底、虚线裁切框），不带任何页面框架；
- 台账页另有**「打印巡检码」批量打印**：按当前筛选一次输出全部设备的标签纸网格，裁开后逐台粘贴——首次铺码时不必逐台点开；
- 打印能力对变压器、电梯、消防三类台账一致（同一套标签组件与打印模式）；
- URL 只含资产 id，重新打印不作废；资产注销后扫码页提示「设备已注销」。

### 3.3 扫码流程

1. 手机相机扫码 → 浏览器打开巡检页（移动端优先布局）；
2. 未登录 → 转登录页（现有账号体系），登录后回跳；
3. 校验巡检权限（§3.4）——无权限则提示「无巡检权限，请联系管理员开通」，不显示表单；
4. 页面显示设备名、位置、规格、**上次巡检的时间与状态**——既确认扫对了设备，也提供交接上下文；
5. 填写：运行状态（正常/异常）、异常描述（异常时必填）、现场拍照；
6. 提交 `create_transformer_inspection` → 成功页，可继续扫下一台。

后台的「登记巡检」按钮走同一张表单——不扫码也能补录。

### 3.4 权限

| 操作 | 要求 |
| --- | --- |
| 资产增删改（后台台账） | `require_menu_path("/maintenance/transformer")`——维护菜单权限，与现状一致 |
| **巡检提交** | 登录账号 + **持有巡检权限码 `maintenance:inspect`**（经角色获得，或对个别员工直授 `UserCode`）+ `require_park_access(资产.park_id)`；`Super` 恒可 |
| 巡检读取 | View 按 `ReadScope` 三层过滤，园区范围内可见 |

关键设计有两条：

- **巡检权限是显式授予的独立权限**，用权限码而非菜单承载：巡检员不需要看到后台维护页，管理员在权限管理页把 `maintenance:inspect` 授给角色（如「园区经理」），或对个别巡检员直授即可——符合「显式授予，不靠名字」的纪律（权限模型设计.md §4.4）。它与台账管理权限分离：能扫码填报的人未必能增删设备。
- **数据范围仍是第一层**：即便持有权限码，也只能巡检自己数据范围内园区的设备。前端路由对已登录用户放行，服务端 Reducer 是真正的边界。

## 第四章　页面改动

### 4.1 变压器管理页（后台）：从记录流水改为资产台账

- 列表**一行一台设备**：名称、位置、园区/厂房、规格、容量、最近巡检（状态+时间）、操作；
- 「新增变压器」录入 §2.2 的资产字段；
- 行内操作：**巡检历史**（时间线，逐条状态/巡检人/照片）、**登记巡检**、**巡检码**、编辑、删除。

### 4.2 手机巡检页（新增）

路由 `/maintenance/inspect/transformer/:id`，移动端优先，流程见 §3.3。

### 4.3 园区档案页

设施区块的变压器卡从「最近一条记录」改为**按资产归并**：该厂房各台变压器及其最近巡检状态。

## 第五章　不变式与配套改动

沿用全库既定纪律，实施时逐项落实：

- **删除园区处置清单**：两张新表登记进 `ParkChild`（均为**阻挡**——巡检是真实历史，删了就是丢数据；`ParkChild` 的编译期完备 `match` 与「所有挂园区的表都已登记」测试会强制这一步，漏登记编译失败）；
- **软删除**、`centi_*` 定点数、面向用户的中文错误文案，全部沿用；
- **校验纯函数**：`check_capacity`（非负）、`check_inspection_status`（枚举）、巡检与资产同园区等，一律 `#[pure_function::pure]` 标注，纳入两端完备性测试；
- **权限码目录**：新权限码 `maintenance:inspect` 经 `client_connected` 自愈式种入 `Code` 表，在权限管理页可见可授（参照 `hr:manage` 先例）；
- **数据域订阅**：巡检页路径在 `/maintenance/` 前缀下，复用维护域数据域订阅。SpacetimeDB 的 View 不带参数，做不了「单台资产」粒度的订阅——按域订阅是现有机制下的最小改动，维护域数据量小，可接受；
- **文档同步**：实施后更新 园区管理.md §1.4、权限模型设计.md（新增巡检权限形态）、ARCHITECTURE 三件套（若涉及表计数等）。

## 第七章　设计决策记录

全部待定项已于 2026-08-04 逐条确认，方案定稿：

- 巡检提交权限 = 登录账号 + 显式授予的权限码 `maintenance:inspect` + 园区数据范围（见 §3.4）；
- 容量单位 = **千瓦（kW）**，沿用老系统口径（见 §2.2）；
- 巡检记录**只增不删**——无更新、无删除 Reducer，更正靠补记录（见 §2.3）；
- **本方案仅覆盖变压器，电梯与消防不照搬**——它们对应的实体不同（电梯必须挂到具体厂房与具体位置，消防是按检查点逐项检查而非单台设备），结构须按各自实际单独设计，后续另立方案。
