**作者**：周茂森

## 第一章　现状与问题

现行 `firefighting` 表一行是一个「检查点」，混装两类信息：检查点名称（可空）、园区/厂房归属，加上**灭火器、消防栓、安全通道三列各自的检查状态**与检查人、检查时间。问题除第四篇 §1.2 列过的通病外，多一条自己的：

- **三类设施压在一行里**——一个检查点只能记"一台灭火器+一个消防栓+一个通道"的组合状态，楼层里第二台灭火器就没地方记；哪台灭火器异常、在哪个位置，都表达不出来。

生产数据现状（2026-08-04 实查）：`firefighting` 表 **0 行**，无迁移负担，旧表照例弃置为空壳，旧 Reducer/View 移除。

## 第二章　目标模型：设施挂楼层

### 2.1 与变压器、电梯的关键差异

**消防设施位于园区下某个厂房或宿舍楼的楼层中，一层有若干个设施。**由此定下三条规则：

1. **一行一个设施**——灭火器、消防栓、消防出口各自成行，各有自己的位置与巡检历史；旧模型的"三列状态"由**设施类型**字段取代；
2. **位置必须挂在楼层上，厂房楼层与宿舍楼层二选一**——`factory_floor_id` 与 `dormitory_floor_id` 沿用 0 哨兵约定，**恰好一个非 0**（与水电表 `check_single_location` 同构，但更严格：不允许两者都空）；
3. **园区由楼层推导**——录入界面走 园区 → 厂房 → 楼层（或 园区 → 宿舍楼 → 楼层）级联，服务端沿楼层反查出 `park_id` 落库，客户端不传园区。

### 2.2 消防设施资产表 `firefighting_asset`（新表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `asset_id` | `u64` PK auto_inc | 台账主键，二维码由它生成 |
| `customer_id` | `String` | 运营方隔离 |
| `park_id` | `u64` | 服务端沿楼层推导写入 |
| `factory_floor_id` | `u64` | 厂房楼层，`0` = 不在厂房 |
| `dormitory_floor_id` | `u64` | 宿舍楼层，`0` = 不在宿舍；与上一字段**恰好一个非 0** |
| `facility_type` | `String` | **设施类型**，固定枚举：`灭火器` / `消防栓` / `消防出口` / `应急照明` / `其他`（见 §7 待定项 1） |
| `facility_name` | `String` | **必填**——编号或名称（如「3F 东侧灭火器 2 号」） |
| `location` | `String` | **必填**——楼层内位置描述（如「东侧楼梯口」） |
| `specifications` | `Option<String>` | 型号规格（如「MFZ/ABC4 干粉」） |
| `expiry_on` | `Option<String>` | **有效期至** `YYYY-MM-DD`——设施类型为灭火器时**必填**（服务端校验），其余类型可选 |
| `remark` | `Option<String>` | 备注 |
| `is_deleted` / `created_at` / `updated_at` | — | 软删除与时间戳 |

索引：`by_customer`、`by_park`、`by_factory_floor`、`by_dormitory_floor`。资产图片：`firefighting_asset_image` 关联表 + 带 URL 预览视图（同第四篇模式）。

### 2.3 巡检记录表 `firefighting_inspection`（新表）

与 `transformer_inspection` 完全同构：`asset_id`、`status`（正常/异常）、`abnormal_note`（异常必填）、`inspector_user_id` + `inspector_name` 快照、`check_time`、`remark`、现场照片。**只增不删**。每个设施单独巡检——"这层楼三台灭火器巡了两台"从此有据可查。

### 2.4 位置校验（纯函数）

`check_firefighting_location(factory_floor_id, dormitory_floor_id)`：恰好一个非 0，否则报「消防设施必须挂在一个厂房楼层或宿舍楼层上」。服务端另按楼层存在性反查归属：厂房楼层 → 厂房 → 园区，或宿舍楼层 → 宿舍楼 → 园区。

`check_extinguisher_expiry(facility_type, expiry_on)`：设施类型为灭火器时有效期必填。

### 2.5 有效期到期提醒

**判定放在前端**——SpacetimeDB 的 View 无法获取时间源（这正是会话清扫须以定时任务作为补偿的原因），而资产数据本即实时订阅至前端，前端具备时钟，比较两个 `YYYY-MM-DD` 字符串即可：

- **已到期**（`expiry_on` ≤ 今天）：台账行红色「已到期」徽标、页顶横幅「N 个设施已到期，请及时更换」、统计卡计数；
- **临期**（30 天内到期）：黄色「N 天后到期」提示；
- 手机巡检页打开对应设施时同样显示到期警示——巡检人员扫码即见。

「通知巡检人员」在当前系统能力下即上述**打开即见的醒目提醒**（巡检人员持码，消防页与巡检页都会看到）。短信/推送级别的主动通知依赖 ARCHITECTURE.md §2.10 规划中的事务性发件箱网关，落地后由每日任务扫描到期设施投递短信任务——本篇预留该衔接，不在本轮实现。

## 第三章　巡检二维码

全部复用第四篇第三章机制：码内容 `/maintenance/inspect/firefighting/{asset_id}`，无密钥；权限复用 `maintenance:inspect`（一码通检）；手机巡检页与前两类共用布局。

---

## 第四章　页面改动

- **消防管理页**（后台）：从"检查点流水"改为设施台账——列表一行一个设施（类型徽章 + 名称、园区·楼宇·楼层 + 位置、型号、最近巡检），可按**设施类型**与巡检状态筛选；表单为两段级联（选「厂房 / 宿舍楼」再选楼层）；
- **手机巡检页**：`/maintenance/inspect/firefighting/:id`；
- **园区档案页**设施卡：消防卡按厂房归并（经楼层）——显示该厂房消防设施总数、按类型分布、最近巡检异常数；宿舍楼的设施在台账页按位置筛选查看；
- 数据地图消防节点切换到资产表。

`overview.rs` 通用台账组件此后只剩**报修工单**一个使用者，可顺势简化（工单不是"资产+巡检"结构，保留现有流水模型）。

## 第七章　设计决策记录（2026-08-04 确认）

1. **设施类型枚举**定案：`灭火器 / 消防栓 / 消防出口 / 应急照明 / 其他`；
2. **灭火器设独立「有效期至」字段**，服务端强制必填；到期提醒按 §2.5 落地（前端打开即见的醒目提醒；短信级推送预留给 §2.10 网关）；
3. **没有室外消防设施**——楼层二选一的位置规则不留"园区公共区域"口子；
4. 共同纪律沿用第四篇：巡检只增不删、`maintenance:inspect` 一码通检、软删除、图片同事务。
