# 云园慧控电梯台账与扫码巡检设计方案

**作者**：周茂森

**文档定位**：`docs/` 系统设计文档系列第五篇，经确认后已于 2026-08-04 **实施完毕**（代码全部落地，随下一次正常部署上线）——现在同时是该功能的实现记录。电梯与变压器同属「资产 + 巡检」结构，共同机制（两表分离、巡检只增不删、扫码流程、权限模型、软删除、图片事务）不再重复论证，一律引用第四篇 [变压器台账与扫码巡检.md](变压器台账与扫码巡检.md)；本篇只写电梯的**结构差异**与自身字段。

## 第一章　现状与问题

现行 `elevator` 表（`tables/maintenance/elevator.rs`）与改造前的变压器同病：一行混装资产信息（名称、轿厢尺寸、额定承重、生产日期）与巡检信息（状态、检查人、检查时间），名称还是可空的。问题清单同第四篇 §1.2，不再赘述。

生产数据现状（2026-08-04 实查）：`elevator` 表 **0 行**，无迁移负担，新模型直接取代，旧表弃置为空壳（删表被官方禁止，与第四篇 §2.4 同一处置）。

## 第二章　目标模型：电梯必挂厂房

### 2.1 与变压器的关键差异

**电梯对应的是园区的厂房：一个厂房拥有若干台电梯，电梯不存在「园区公共区域」一说。**由此定下两条规则：

1. `factory_id` **必填非 0**——变压器的 0 哨兵（公共区域）在电梯上不适用；
2. **`park_id` 由厂房推导**——录入界面只选厂房（园区→厂房级联选择），服务端取 `factory.park_id` 落库，客户端不传园区。园区归属跟着厂房走，从结构上排除「电梯挂在 A 厂房、园区却填了 B」的矛盾。

（表上仍保留 `park_id` 列：园区删除清单、数据范围过滤都按园区索引，且这是全库惯例。）

### 2.2 电梯资产表 `elevator_asset`（新表）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `asset_id` | `u64` PK auto_inc | 台账主键，二维码由它生成 |
| `customer_id` | `String` | 运营方隔离 |
| `park_id` | `u64` | 服务端从厂房推导写入，不接受客户端直传 |
| `factory_id` | `u64` | **必填非 0**——电梯必须属于某个厂房 |
| `elevator_name` | `String` | **必填**（如「A 座 1 号客梯」） |
| `location` | `String` | **必填**——厂房内位置描述（如「东侧大厅」） |
| `size` | `Option<String>` | 轿厢尺寸（长 × 宽 × 高） |
| `load_capacity_centi_kg` | `u64` | 额定承重，单位**千克（kg）**，×100 整数存储（沿用现表口径） |
| `production_date` | `Option<String>` | 生产日期 `YYYY-MM-DD`（现表用 Timestamp，新表统一为日期字符串，与厂房建造时间同口径） |
| `remark` | `Option<String>` | 备注（维保单位、联系电话等可先记这里，见 §7 待定项 1） |
| `is_deleted` / `created_at` / `updated_at` | — | 软删除与时间戳 |

索引：`by_customer`、`by_park`、`by_factory`。资产图片：`elevator_asset_image` 关联表 + 带 URL 预览视图（同第四篇模式）。

### 2.3 巡检记录表 `elevator_inspection`（新表）

字段与 `transformer_inspection` 完全同构：`asset_id` 必填外键、`status`（正常/异常）、`abnormal_note`（异常必填）、`inspector_user_id` + `inspector_name`（登录会话快照）、`check_time`、`remark`、现场照片关联表。**只增不删**，纪律同第四篇 §2.3。

## 第三章　巡检二维码

全部复用第四篇第三章的机制，仅路径不同：

- 码内容：`https://yz.furong.org/maintenance/inspect/elevator/{asset_id}`，无密钥；
- 权限：**复用同一个权限码 `maintenance:inspect`**——它叫「设施巡检」，本来就为整个维护域设计，不为电梯单设权限码（巡检员通常同时管几类设备，一码通检）；
- 提交门卫：登录 + 持码（Super 恒可）+ 园区数据范围；
- 手机巡检页 `/maintenance/inspect/elevator/:id`，与变压器巡检页共用布局与表单结构。

## 第四章　页面改动

- **电梯管理页**（后台）：从记录流水改为资产台账，与变压器管理页同构——列表一行一台（名称、厂房、位置、尺寸/承重、最近巡检），操作为登记巡检 / 巡检历史 / 巡检码 / 编辑 / 注销；表单只选厂房不选园区（§2.1）；
- **园区档案页**设施卡：电梯卡按资产归并——该厂房各台电梯与最近巡检，多于一台时提示「共 N 台」；
- 数据地图电梯节点切换到资产表。

## 第五章　不变式

同第四篇 §5，逐项照办：`elevator_asset` 登记进园区删除清单（阻挡，「条运维记录」，编译期完备 match 强制）；`check_*` 校验纯函数并入完备性测试；维护域订阅换新视图；旧 `elevator` 表弃置、旧 Reducer/View 移除。电梯专属校验一条：**厂房必填且必须存在**（`require_factory`，园区随之推导）。

## 第七章　设计决策记录（2026-08-04 确认）

1. **字段清单**：按 §2.2 实施；维保单位、维保电话、年检到期日**暂不设独立字段**，先记备注——需要按年检到期排序提醒时再加列（带默认值的追加列属安全迁移，见 ARCHITECTURE.md §2.6.1）。
2. **额定承重单位**：**千克（kg）**，沿用现表口径，展示如 `2000.00 kg`。
3. **共同纪律沿用第四篇已定项**：巡检只增不删、复用 `maintenance:inspect` 权限码（一码通检）、软删除、图片同事务。
